# Velo Engage — Project Status Report

*Prepared as a working-session summary of what has been built, fixed, and verified so far, and what remains before the platform matches the full master specification.*

---

## 1. What Velo Engage is

Velo Engage is a revenue-recovery and proactive-care engine for clinics. It automatically:

1. **Detects** patients who have a reason to be contacted (lapsed care, clinical recall, open treatment plans, benefit expiry, etc. — 15 "opportunity families").
2. **Gates** each opportunity on consent, opt-out status, and message-frequency limits.
3. **Ranks** patients by expected value (how likely they are to respond, weighted by clinical/commercial priority) and randomly assigns a small holdout group that receives no message, so the clinic can prove the campaign caused the bookings.
4. **Reaches out** on WhatsApp (with SMS fallback) using pre-approved templates.
5. **Measures** delivery, replies, bookings, attendance, and revenue, feeding it all back into a live dashboard.

The system runs as a set of containerized services orchestrated by Temporal, with Postgres as the system of record, NATS for messaging between services, Neo4j for a clinical-recall knowledge graph, MLflow for model tracking, and a server-rendered console for the clinic owner.

## 3. What has been fixed and built this session

### 3.1 Core pipeline reliability
- Fixed the `ve_reach` webhook handler: correctly parses Meta's real payload shape (`entry[].changes[].value.{messages[],statuses[]}`), moved `/health` and `/send-test` back to being real routes, added the missing opt-out handler, fixed the malformed exception handling.

- **Result, verified live:** the full pipeline (rules → consent/frequency gating → holdout split → dispatch → WhatsApp → webhook → outcome recording) now runs end-to-end without errors on every trigger.

### 3.2 Wired all 15 opportunity families into the live pipeline
- Replaced the hardcoded 3-family rule list with the existing (previously unused) YAML policy engine, which evaluates every family in `policies/opportunities/*.yml` against real patient data.
- **Safety consequence caught and fixed:** wiring in 12 more families at once caused a single run to attempt dispatching 5,214 WhatsApp messages instantly (harmless only because a token happened to be expired). Implemented the `WORKFLOW_BATCH_LIMIT` and `DISPATCH_LIMIT` safety caps that were declared in configuration but never actually enforced in code, and purged the resulting NATS backlog so it couldn't fire all at once later.

### 3.3 Guard: consent, cooldown, frequency cap, de-duplication
Previously, gating only checked consent. Now the same activity also enforces:
- A **3-day cooldown** — a patient just contacted can't be contacted again immediately, regardless of how many other opportunities they match.
- A **rolling cap of 3 contacts per 30 days** per patient.
- **One primary opportunity per patient per run** — when a patient matches multiple families simultaneously, only the highest-priority one is acted on. Clinical families are already configured with higher priority values than commercial ones in the YAML, so this naturally enforces "clinical outranks commercial" as the spec requires.

All three are verified live in the orchestrator logs (patients being correctly blocked with clear reasons).

### 3.4 VE Graph — real Neo4j clinical-recall graph
- Seeded a real graph: `(:Condition)-[:REQUIRES_FOLLOWUP {interval_days, evidence_source}]->(:Service)`, age-band screening rules, and `(:Service)-[:DELIVERED_BY]->(:Specialty)` referral mapping — matching the actual condition codes present in the patient data (diabetes, hypertension, asthma, CKD, etc.).
- Family B (clinical recall) now queries this graph live to compute *which* recall is due and how overdue it is, per patient, instead of relying on a flat pre-seeded true/false flag. Falls back to the old flag safely if Neo4j is unreachable.
- Caught and fixed a real bug in the first version of this query (a Cypher join was pairing services with the wrong specialty) before considering it done.

### 3.5 ML models wired into live decisioning
Two trained models existed in MLflow already but were completely disconnected from the live system — the exact same class of bug as the `ve_reach` crash (missing package in the Docker image), compounded by a second bug (both scorers referenced a non-existent MLflow stage called `"latest"`).

- **No-show risk model** (`ve_noshow_v1`, CatBoost) — now loads and scores real patients on every run.
- **Reactivation/response propensity model** (`velo_engage_booking_propensity`, LightGBM) — discovered it had actually been trained on the wrong target (`read_label`, i.e. "will they read the message") instead of the intended `booked_label` ("will they book"). Retrained it correctly, built the missing scorer module, and wired it into ranking.
- Fixed a follow-on bug where LightGBM's compiled extension needs the system `libgomp` library, missing from the slim Docker image.
- **SHAP explainability**: the campaign detail page in the console now shows "why this no-show score" with real per-patient feature contributions (e.g., confirmed live: new-patient status and no deposit paid both correctly push risk up).
- **PSI drift monitoring**: a real Population Stability Index calculation over the no-show model's prediction history, surfaced on the `/models` page. Currently reports "not enough data" because the synthetic dataset was bulk-seeded in a tight time window — this is a correct, honest response given the data shape, not a bug.
- **Redis online feature cache**: the per-clinic feature read is now cached with a 5-minute TTL (Redis was running, unused, before this) with a safe fallback to Postgres on any cache error.

### 3.5b Value and Uplift models (completing the EV formula)
Two more Phase 1/3 models from the master spec, built from scratch and wired into live ranking in this pass.

- **Value model** (`E[revenue | reactivate]`) — investigated *before* training rather than after: found that whether a booked patient generates any revenue at all is driven by attendance, which in the current synthetic dataset is generated as a fixed-probability coin flip independent of every patient feature. No classifier can beat that — so rather than deploy a model that can't outperform a constant, the "gate" half is an empirical base rate, clearly documented as a heuristic, not a disguised no-op model. The "amount" half (how much, given revenue occurs) *is* cleanly determined by `family + high_value_patient + insurance_tier`, and the trained regressor for it works well (MAE dropped from 91.76 to 0.65 currency units once the right features were used).
- **Uplift/causal model** — a T-learner (two classifiers, one trained only on treated campaigns, one only on holdout/control) estimating how much of a patient's booking likelihood is actually *caused* by contacting them, versus patients who'd book anyway or are unmoved either way. This is the actual reason the mandatory holdout exists, and there was finally enough real data to build it: 67,760 treated vs. 11,999 control rows, with a clear, real, measured lift (1.78% vs. 0.63% booking rate). Both arm classifiers trained with strong AUC (0.82 each).
- **Full expected-value ranking**: campaigns are now ranked by `priority_score × booking_propensity_score × value_score`, discounted 10x for patients the uplift model estimates would book anyway or aren't moved by contact (`uplift_score <= 0`) — the complete master-spec EV formula (minus contact/incentive cost terms, which aren't modeled). Verified live and mathematically checked against the stored per-patient scores.
- All four models (no-show, propensity, value, uplift) confirmed scoring successfully together on the same live pipeline run, with the holdout safety gate still showing zero new violations afterward.

### 3.18 Epic OAuth — resolved, and a real data-model discovery underneath it

The remaining failure from §3.6 turned out to have a mundane root cause: the code never logged Epic's actual rejection body (`resp.raise_for_status()` with no `try`/`except`, no `response.text` logging) — every attempt just crashed generically, so neither we nor Epic support could tell *which* rejection this was. Fixed that first (surfaces Epic's real `error`/`error_description` directly in the browser response now, not just docker logs), which is what actually unblocked diagnosis.

Also had to swap the single reserved ngrok tunnel from `ve_reach` to `ve_connect` to even reach the callback handler (documented two-endpoints-one-domain limitation from §3.8/§3.10) — swapped back to `ve_reach` once testing finished, confirmed via `curl` that WhatsApp's webhook path is live again.

**Result: a real, complete login → token exchange succeeded.** `epic_tokens` now holds a genuine RS256 JWT access token, a working refresh token (the `offline_access` scope was honored), and Epic granted a broader scope set than requested (`Appointment`, `DiagnosticReport`, `Observation`, `MedicationRequest`, etc. — not just the handful in `EPIC_SCOPES`).

**A second real bug caught immediately while verifying the token actually works, not just that it exists**: `get_valid_token()` crashed every time with `TypeError: can't compare offset-naive and offset-aware datetimes` — `datetime.utcnow()` (naive) was being compared against `expires_at` read back from Postgres as a timezone-aware value (a `timestamptz` column). Fixed both the write side (`_store_tokens`) and read side (`get_valid_token`) to use `datetime.now(timezone.utc)` consistently. Without this fix, authorization would have looked complete while every actual use of the token still failed.

**A genuine architecture discovery, not a bug, found by testing an actual data pull**: `pull_patient_cohort()` assumed Epic would allow a bulk "list all active patients" query. It doesn't — live sandbox error: `"This resource requires demographics or _id parameter for searching."` Tried the standard workaround (discover patients via `Encounter` search over a date range, then resolve each `Patient` by `_id`) and hit the identical restriction one level down: `Encounter` search *also* requires a specific `patient` or `_id` parameter. This app's current Epic registration is authorized for **per-patient lookups**, not population-level queries — by design, not misconfiguration. Real bulk population pulls from Epic go through a completely separate mechanism (FHIR Bulk Data Export / `$export`), which requires its own App Orchard registration as a Backend System app, JWT-based system-to-system authentication (no user login at all), and separate Epic approval — genuinely external, Epic-administrative work, not something to build around from the code side. Rebuilt `pull_patient_cohort()`/`_discover_patient_ids()` to use the Encounter-then-resolve-by-_id pattern anyway (the architecturally correct shape for when broader access is eventually approved), and added the same missing-error-body logging to `fhir_client.py` that fixed the OAuth diagnosis, so any future Epic rejection here is immediately diagnosable too.

**Status**: Epic OAuth (the actual, long-standing blocker) is fully resolved and verified with a real stored, working, refreshable token. Bulk cohort ingestion needs a separate Epic Bulk Data Export registration — documented as a genuine external follow-up, not attempted further this session per an explicit choice to stop once the real blocker (OAuth) was cleared.

### 3.25 Found and fixed: synthetic patients were crowding real Epic patients out of the daily pipeline entirely

Asked to make every page's numbers genuinely real (not just "queried from Postgres," which they already were, but free of synthetic contamination), an audit of `ve_console/main.py` turned up something much bigger than a display issue.

**Root cause, confirmed with real data before fixing anything**: `ve_orchestrator`'s `evaluate_rules()` activity (via `feature_store.fetch_patient_features()`) evaluated *every* row in `patient_features` on every run — all ~20,000 `SYN*`/`P0xx` synthetic patients alongside the 7 real Epic ones, with no distinction. Since the pipeline had been running daily for roughly two weeks, this had already written **314,631 `SYN*`-patient opportunity rows and 67,334 `SYN*`/`P0xx`-patient campaign rows in the real (non-`syn_`-prefixed) ID format** — indistinguishable from genuine pipeline output by the console's existing `syn_opp_`/`syn_campaign_`-prefix filter, which only ever caught the original one-time fabricated seed rows, not this ongoing contamination. Worse, this wasn't just a cosmetic problem: with 20,000 synthetic patients competing for the same `WORKFLOW_BATCH_LIMIT=25` every run, a live trigger confirmed real Epic patients had real matching opportunities but **zero of them became campaigns** — entirely crowded out by synthetic volume.

**Fix, in two layers**:
1. **Root cause** (`ve_orchestrator/feature_store.py`): `fetch_patient_features()` now excludes `patient_id LIKE 'SYN%'` and `LIKE 'P0%'` at the Postgres query itself, so synthetic/seed patients are never evaluated by the live pipeline again. Existing synthetic rows/history untouched, per the earlier explicit decision not to delete anything.
2. **Display layer** (`ve_console/main.py`): the `_REAL_OPPORTUNITY`/`_REAL_CAMPAIGN`/`_real_or_unattributed_campaign` filters (used across every page) now also exclude by `patient_id` prefix, not just by `opportunity_id`/`campaign_id` prefix — closing the exact gap that let the 382,000 contaminated rows through. Applied consistently to `/overview`, `/opportunities`, `/campaigns`, `/whatsapp` (both the `outbound_messages` and `inbound_messages` queries, and the `manual_test` metrics), `/bookings`, `/revenue`, `/holdout`, and `/models`' drift-monitoring query — the only page intentionally left unfiltered is `/models`' MLflow training-run listing, since those runs genuinely were (and still should be) trained on the synthetic outcome history.

**Bug introduced and caught during the fix itself**: initially added the `patient_id` clause directly inside the `_REAL_CAMPAIGN`/`_REAL_OPPORTUNITY` string constants, not realizing three call sites glued a table alias directly onto them as `c.{_REAL_CAMPAIGN}` — a trick that only worked when the constant was a single unprefixed condition. With multiple `AND`-joined conditions now inside it, that pattern would have produced ambiguous-column SQL errors on any multi-table join. Found by grepping for every usage before rebuilding, not by waiting for a runtime error; fixed by switching those three sites to the existing `_real_campaign("c")` function form, which prefixes every condition correctly.

**Also caught during verification**: the first two post-fix pipeline triggers still produced synthetic-patient campaigns — not because the fix was wrong, but because `ve_orchestrator` had been rebuilt *before* this particular edit was made and was never rebuilt again afterward, so the running container was silently still on the old code. Caught by directly inspecting the running container's loaded source (`docker exec ve_orchestrator python3 -c "import inspect; ..."`) rather than assuming the fix was live just because the file on disk was correct.

**Verified live, end-to-end, after the actual fix was deployed and the stale Redis feature cache flushed**: a fresh trigger produced `{"opportunities_found":11,"passed_consent":7,"campaigns_created":7,"dispatched":1}` — all 7 campaigns confirmed in Postgres to belong to real Epic `patient_id`s (e.g. `erXuFYUfucBZaryVksYEcMg3`, `eIXesllypH3M9tAA5WdJftQ3`), correctly split across treated/holdout arms, zero synthetic patients involved. The single `dispatched:1` count did not produce a visible WhatsApp send because `ve_reach` correctly skipped it — that specific real patient (Desiree Powell) has no phone number on file in Epic's sandbox record (`"No phone found for eAB3mDIBBcyUKviyzrxsnAw3 — skipping"`), a genuine sandbox data-completeness gap, not a pipeline defect (same category of Epic sandbox sparsity already documented in §3.20/§3.21).

**Models were explicitly left untouched, by user decision**: no retraining was done — the 7 real Epic patients have no outcome/campaign history yet to train on, so the existing models (trained on the synthetic outcome history, which does have real labels) continue to score real Epic patients via inference, exactly as they already did before this fix. Retraining remains a future step once real campaigns accumulate real outcomes over time.

### 3.9 `ve_reach`'s NATS subscriber could die silently on a cold start — fixed
Found by manually triggering the pipeline and noticing a dispatched campaign never reached WhatsApp: `ve_orchestrator` logged a successful publish, but `ve_reach` never logged "Processing campaign," and NATS JetStream showed the `campaigns` stream with 0 consumers attached. | Model | Metric | Before | After |
|---|---|---|---|
| No-show risk (CatBoost) | Test AUC | 0.676 | 0.676 |
| No-show risk | Test Brier score (calibration) | 0.236 | **0.189** |
| Booking propensity (LightGBM) | Test AUC | 0.643 | **0.889** |
| Booking propensity | Test AUC-PR | 0.182 | **0.315** |
| Uplift — treated arm | Test AUC | 0.825 | **0.901** |
| Uplift — control arm | Test AUC | 0.821 | 0.798 (honest re-estimate, see below) |

**No-show model**: expanded from 19 to 32 booking-time-safe features (added real historical aggregates — `hist_noshow_rate_90d/365d`, `days_since_last_noshow`, prior WhatsApp-confirm rate, etc. — checked each for leakage via point-biserial correlation against the label before adding any; all in the 0.02-0.11 range, nothing near the ~0.39-1.0 that flags the columns correctly left out, like `outcome_state` and `no_show_probability`). A hyperparameter sweep (depth, learning rate, class weights, iterations) confirmed ~0.676 AUC is close to the real ceiling for this dataset's booking-time signal — every configuration converged there. The real win was fixing calibration: the old `class_weights={0:1,1:3}` skewed predicted probabilities so far toward "no-show" that precision on the "show" class had collapsed to 5% recall; a milder weighting plus a validation-set F1-optimal decision threshold (replacing a stale hardcoded 0.27) fixed both the Brier score and the classification report.

**Booking propensity + uplift models**: found the real cause of weak metrics — `previous_reads`/`previous_replies`/`previous_bookings`/`previous_campaigns` (strongly correlated with booking, 0.15-0.33) existed only in the synthetic seed script's fabricated `rule_evidence`, meaning they were **always null for every live-detected opportunity** (the real orchestrator never populates them) — a model trained on them would look great offline and be useless in production. Fixed properly rather than just adding the field: both `ml/feature_pipelines/build_training_dataset.py` and `activities.py`'s `rank_and_assign_holdout` now compute these as real prior-campaign counts via a SQL window function over `campaigns`/`outcomes`, strictly ordered before each row (no leakage from a campaign's own outcome) — identical logic in both places, so training and live scoring see the same feature definition.

Also **quadrupled the synthetic population** (5,000 → 20,000 patients in `scripts/seed_synthetic_phase1.py`) — the live (non-synthetic) campaign rows have a near-zero booking rate right now (no real booking-attribution loop closes yet), so nearly all trainable signal comes from the synthetic population; more of it directly reduces the variance in these estimates and gives the uplift model's data-starved control arm (previously ~76 positives total) meaningfully more to learn from.

**Caught a real evaluation-integrity bug before trusting the first round of numbers**: patients can have many near-duplicate campaign rows (repeat seed-script runs on different calendar days share identical outcomes for the same random seed; repeated live-pipeline triggers during this session added more). A plain random train/test split can put near-duplicate rows for the same patient on both sides, inflating test AUC through leakage rather than genuine generalization. Switched all three models (`train_propensity.py`, `train_uplift_model.py`, `train_value_model.py`) from `train_test_split` to `GroupShuffleSplit` grouped by `patient_id`. The propensity AUC barely moved under the honest split (0.890 → 0.889 — reassuring: it means the model is learning a patient-invariant pattern, not memorizing duplicates), but the uplift control arm's estimate dropped from an inflated 0.835/0.155 to an honest 0.798/0.093 — a real, if less flattering, number.

**Two honest limitations, not fixed this pass**:
- The no-show model's 13 new historical fields (`hist_noshow_rate_90d`, etc.) only exist in its disconnected external training CSV — the live `patient_features` Postgres table has no equivalent columns, so at live-scoring time they fall back to neutral defaults for every real patient. The offline metric improvement (Brier score, calibration) is real and does apply live via the core fields that were already connected; the new historical fields themselves are currently inert in production. Making them live would need a new ETL computing rolling no-show aggregates from real appointment history — a real Phase 2 item, not attempted here.
- The uplift control arm remains data-starved (196 positives after quadrupling the population) — this is an honest reflection of how rare organic (uncontacted) bookings genuinely are in the simulation, not a modeling shortfall; it would need an even larger synthetic population or, better, real production data to resolve properly.

### 3.13 Real bug: the batch-limit cap silently locked every run to a single family

Reported by the user after triggering the pipeline repeatedly and noticing every run only ever touched one family at one priority value. Root cause in `evaluate_rules()` (`services/ve_orchestrator/src/ve_orchestrator/activities.py`): every real match across all 15 families gets written to `opportunities` regardless of any cap (correct), but the *batch* that flows into `gate_consent`/ranking downstream was built by sorting all matches by raw `priority_score` — a fixed constant per family from the YAML policies (family C is always `0.9`) — and truncating to `WORKFLOW_BATCH_LIMIT` (25). Since family C alone produces tens of thousands of matches every run, a plain sort-by-priority-then-truncate returns **100% family C, every single time** — every other family, and the real ML-based expected-value ranking downstream, never got a chance to see a diverse candidate pool.

Fixed by round-robining across families instead of a flat truncation: group matches by family, then take one from each family per round (families still visited in priority order within each round, so clinical still edges out commercial at the margin) until the cap is reached. **Verified live**: a direct test of `evaluate_rules()` now returns all 15 families in one 25-opportunity batch (2 each for the first 10, 1 each for the rest) spanning 15 distinct priority values, instead of 25 identical family-C/priority-0.9 rows. A subsequent real pipeline trigger produced campaigns in families J and Q — families that were structurally impossible to reach before this fix.

### 3.17 Vault secrets management — every service's credentials now flow through Vault

Before this pass, Vault had been running healthy since early in the project but genuinely unused — every credential (Postgres, Neo4j, Keycloak client/session secrets, WhatsApp access token, Twilio, Epic client secret, ngrok authtoken) lived as plaintext in `.env` files and inline `docker-compose.dev.yml` environment blocks. **A real, load-bearing limitation caught before it became a silent landmine**: Vault here runs in dev mode (`vault status` confirms `Storage Type: inmem`), which is *hardcoded* to in-memory storage — every secret is lost on a Vault container restart, full stop, no config flag changes that. ## 8. Survival / Time-to-Need Model — DONE, verified end-to-end

Predicts days-to-book after a campaign is dispatched, per the master spec's Phase 2 "optimal send timing" item. Framed honestly as what the data actually supports: this is *response latency after contact* (dispatch → booking), not a patient's true underlying recall cadence independent of any outreach — the schema has no per-patient visit-history event log to derive the latter from. Still directly useful for the stated goal: patient profiles predicted to convert slowly are candidates for earlier/more-persistent outreach.

### 8.1 The real blocker found before writing any model code
Investigated the actual duration data before training anything, per this session's practice of verifying against real data rather than assuming. Found something worse than "thin data": average gap between campaign creation and a booked outcome being recorded was **~0.002 days** (a few minutes) across all 4,884 booked outcomes, and **zero** real (non-synthetic) patients had any booked outcome at all. Root cause: `outcomes` had a single `recorded_at` timestamp shared by *every* stage (delivered/read/replied/booked/attended) — every webhook update clobbered the previous stage's real timing, so no duration between any two stages could ever be recovered, for real or synthetic data. This was a structural data-model gap, not something a training script could work around. Given the choice between fixing the data model first, switching to a different missing piece, or shipping a placeholder trained on noise, the data-model fix was chosen.

### 8.2 Data model fix
- **`infra/migrations/015_outcome_stage_timestamps.sql`**: added `delivered_at`/`read_at`/`replied_at`/`booked_at`/`attended_at` to `outcomes`.
- **`services/ve_reach/src/ve_reach/db.py`** (`upsert_outcome()` and the reply-specific upsert): each per-stage timestamp is now set only the *first* time that stage becomes true (`CASE WHEN` on insert, `COALESCE` on conflict) — a naive `= now()` on every call would keep clobbering earlier stages' real timing with whatever the latest webhook call happened to be, exactly the bug that made this impossible before.
- **`services/ve_measure/src/ve_measure/booking_listener.py`**: `booked_at`/`attended_at` now use the real `occurred_at` event time already available from the source booking event, not `now()` (the time this handler happened to run).
- **`scripts/seed_synthetic_phase1.py`**: previously set every stage instantly with `recorded_at=now()` and a fixed `appointment_date = today + 7 days` for every booking. Rewrote to simulate realistic per-stage delays — exponential waiting times (`stage_delay()`) whose mean scales inversely with each simulated patient's existing `engagement_score`, so more-engaged patients realistically respond and book faster, giving genuine learnable variance instead of a constant. **Correctness issue caught and fixed before running it**: the new random draws would have consumed from the same `random` module stream the file's `random.seed(42)` reproducibility guarantee depends on, silently changing every existing synthetic patient's delivered/read/replied/booked/attended outcome on a re-run. Fixed with a separate `TIMING_RNG = random.Random(1337)` stream for only the new timing draws. **A second bug caught from the data itself**: the holdout arm's `booked_at` was first anchored to midnight-today, which could land *before* `campaigns.created_at` (set to real "now" whenever the script runs) when the random delay was small and the script ran late in the day — produced a real negative-duration row (`min_hours: -21.4`) that was caught by inspecting the actual output distribution, not by code review. Fixed by anchoring both arms to the same captured instant.
- **Re-ran the seed script live**: confirmed via a before/after diff of every synthetic patient's boolean outcome columns that the fix didn't change any existing row (campaign IDs embed the run date, so re-running only adds a new day's batch) — then confirmed the new timestamps have real variance (avg ~6.1 days, stddev ~8.7 days, min 0.03 days, max 82 days) once the negative-duration bug was fixed.

### 8.3 Model
- **`ml/feature_pipelines/build_training_dataset.py`**: added `out.booked_at` to the existing SQL join — no other changes needed, `campaign_created_at` was already selected.
- **`ml/training/train_survival_model.py`**: LightGBM regression on `log1p(days_to_book)`, same feature set as `train_propensity.py` (whether a patient converts and how long it takes are the same underlying engagement signal), `GroupShuffleSplit` by `patient_id` matching every other model here. Deliberately **no new survival-analysis dependency** (`lifelines`/`scikit-survival`) — per team decision, matching this codebase's existing pattern of pragmatic, honestly-documented approximations over new infrastructure (`train_value_model.py`'s heuristic base rate is the direct precedent). Right-censored patients (haven't booked yet) are simply excluded, a documented simplification. Trained on 3,603 real-timing examples (only today's freshly-simulated batch has the new columns — the ~5,000 pre-existing historical synthetic rows don't), MAE ~4.88 days, RMSE ~8.64 days against a target with mean ~6.1 days — meaningfully better than predicting a constant.
- **`ml/registry/survival_scorer.py`**: same `resolve_production_version()` pattern as every other scorer, `score_opportunities_batch()` returning predicted days-to-book. Registered as `velo_engage_survival`, promoted to Production, verified against two live feature rows — a more-engaged profile correctly predicted faster conversion (5.7 days) than a less-engaged one (9.8 days).

### 8.4 Wiring — informational, not blended into ranking
- **`infra/migrations/016_survival_score.sql`**: new `survival_score` column on `campaigns`.
- **`services/ve_orchestrator/src/ve_orchestrator/activities.py`**: added as a fifth scorer alongside noshow/propensity/value/uplift in `rank_and_assign_holdout`, same try/except-falls-back-gracefully pattern (falls back to `None`/unscored on failure, since unlike the other four scores there's no natural neutral multiplier for a duration estimate). **Deliberately not folded into `expected_value`** — persisted and monitored, but blending a duration estimate into a per-contact EV formula needs its own deliberate mathematical treatment (e.g. discounting later conversions), a separate design decision from training the model itself.
- **`services/ve_console/src/ve_console/main.py`**: one new `REGISTERED_MODELS` entry (`velo_engage_survival` / `survival_score`) — picked up generically by the existing `/models` page loop, drift monitoring (`_score_drift`), and quality-metric exclusion (correctly absent from `_QUALITY_QUERIES`, same as value/uplift, since a duration doesn't map onto classification metrics).
- **Verified end-to-end live**: triggered the real daily Temporal pipeline, confirmed `"ML scored 7 patients (predicted days-to-book)"` in the orchestrator logs with no errors, confirmed real `survival_score` values landed in `campaigns` for all 7 real patients, and confirmed `/models` renders the new card correctly (real MAE/RMSE metrics, honest `insufficient_data` drift status since only 7 real campaigns are scored so far, quality metrics correctly excluded).

## 9. Lookalike / Collaborative-Filtering (Cross-Sell) Model — DONE, verified end-to-end

Feeds family D's "cross-specialty" detection (`policies/opportunities/D.yml`, tagged `methods: [R, D, AI]` — only the `[R]` rule existed before this; this is the `[AI]` piece). Unlike every other model in this project, it doesn't score opportunities the rule engine already found — it generates new ones: for each patient, which opportunity family they've never engaged with are they nonetheless likely to respond well to, based on patterns from other patients.

### 9.1 A real negative result, investigated rather than shipped
First attempt used `sklearn.decomposition.NMF` — genuine matrix factorization over a patient × family interaction matrix, no new dependency needed. Held-out evaluation (properly implemented: patients split into train/eval groups, family embeddings learned only from training patients, eval patients projected in via `NMF.transform()` using their own held-out-one-family-hidden history) scored **AUC 0.29 — worse than random**, not just weak. Investigated why before concluding anything was broken, rather than assuming a bug or silently shipping it: **74% of patients with any booked-family history (2,334 of 3,163) have booked for exactly one family, ever**; only 829 have 2+, almost all with exactly 2. Matrix factorization needs patients with multiple item interactions to discover which patients are "similar" — with three-quarters of the base having a single data point, there's no cross-family correlation signal for any embedding method to find yet. Confirmed this was a data-density limitation, not a code bug, by ruling out the obvious alternative explanation first (an earlier, incorrect version of the eval that zeroed held-out cells directly in the training matrix — which teaches vanilla NMF to predict low scores exactly there, since it has no concept of "unknown" versus "true negative" — also scored a suspicious ~0.28, but the *corrected*, leak-free per-patient-split version scored the same, ruling out that explanation).

### 9.2 Shipped instead: an honest co-occurrence heuristic
Per user decision, not a trained embedding model — a documented heuristic, same precedent as the value model's `revenue_base_rate`. `ml/training/train_lookalike_model.py` computes real family-to-family conditional probabilities directly (P(patient also has family Y | patient has family X)) from the same interaction matrix, gated by a minimum-support threshold (`MIN_SUPPORT = 5`) so rare, noisy pairs don't drive recommendations. Evaluated with the same leak-free per-patient leave-one-out split as the (failed) NMF attempt — **held-out AUC 0.86**, a genuinely strong result, confirming the earlier failure really was a method/data-sparsity mismatch and not unlearnable data: co-occurrence needs far less per-patient history than embeddings to find real pairwise structure. Registered as `velo_engage_lookalike`, promoted to Production.

### 9.3 Threshold policy
Per explicit user decision: only the **top ~10% most confident** recommendations (90th percentile of candidate scores) actually generate outreach — a real WhatsApp message to a real patient shouldn't go out on a weak signal from a model with no long-run validation yet. `affinity_threshold` is computed at training time and read back from the MLflow run, same pattern as `value_scorer.py`'s `revenue_base_rate`.

### 9.4 Wiring — generates new opportunities, not just scores
- **`ml/registry/lookalike_scorer.py`**: `recommend_families_batch()` — one call per pipeline run, returns `(recommended_family, score)` or `None` per patient (cold-start patients with zero known-family history correctly get `None`, not a fabricated score).
- **`services/ve_orchestrator/src/ve_orchestrator/activities.py`**: extended inside `evaluate_rules()` itself (not a separate step) — a live batched query gets every patient's known-booked families, the scorer recommends per patient, and above-threshold recommendations are appended to the *same* `matches`/`insert_rows` lists the YAML rule engine populates, tagged `family='D'` with `rule_name='lookalike_cross_specialty'`, reusing family D's own `consent_class`/`priority` from its YAML (so it's additional evidence for the same cross-specialty concept, not a separate family). This means it flows through the existing round-robin batching, consent gating, and holdout assignment identically to rule-based opportunities, with no special-casing downstream. Wrapped in the same try/except-log-and-continue pattern as every other scorer call — a lookalike failure never blocks the rule-based families.
- **`services/ve_console/src/ve_console/main.py`**: one new `REGISTERED_MODELS` entry, `score_column: None` (same as the intent classifier) — this model's output lives in `opportunities.rule_evidence`, not a `campaigns` column, so there's nothing for `/models`' drift monitoring to track per-campaign; correctly excluded from both drift and the classification-quality metrics (same reasoning as value/uplift/survival — its output doesn't map onto either).
- **11 new unit tests** covering the heuristic's pure logic (co-occurrence computation, minimum-support gating, cold-start handling) and the scorer's batching/threshold behavior — all passing, full suite now 106.
- **Verified end-to-end live**: triggered the real daily pipeline, confirmed `"Lookalike scored 7 patients, 0 new cross-specialty recommendations above threshold"` in the orchestrator logs with no errors — correct, expected output, since the 7 real patients don't have any booked-family history yet for the heuristic to work from (same data reality the survival model hit). Separately confirmed the underlying logic does produce real, sensible recommendations once history exists: a patient known only for family A live-scores a recommendation for family C at 0.20 affinity, above the 0.156 threshold — using the exact same code path the live pipeline calls.
